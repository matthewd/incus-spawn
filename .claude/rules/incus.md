# Incus Interaction

`IncusClient` communicates with the Incus daemon via its REST API. On Linux, requests go over a Unix domain socket (`UnixSocketTransport`); on macOS, over a vsock tunnel exposed as a Unix socket (same `UnixSocketTransport`). `IncusApi.tryConnect()` selects Linux Unix sockets -> vsock Unix socket; there is no HTTPS fallback (the old HTTPS-over-TCP path was removed -- it hit macOS Local Network prompts and VPN socket filters, and two transports made field issues undiagnosable; `HttpsTransport` remains in the tree but is unwired). `IncusApi` handles request serialization, async operation waiting, and WebSocket-based exec (capture, stream, PTY). `Container` is a helper for running commands inside a specific container (`exec`, `runAsUser`, `runInteractive`). The `incus` CLI binary is not required at runtime.

**macOS vsock robustness**: the vfkit vsock tunnel does not reliably propagate connection close/EOF, which drives several design choices (see DESIGN.md "Transport" and appliance/DESIGN.md):
- **Exec completion via `/wait`, not close frames.** `IncusApi.execWebSocket` unifies capture/stream/bidirectional exec and takes the operation `/wait` endpoint (daemon operation state over HTTP) as the authoritative completion + exit-code signal, then drains and force-closes the data sockets -- so a lost close frame can't hang exec. Every exec fd is keepalive-pinged; the drain is adaptive.
- **Keep-alive connection cache.** Short request-path calls (`get`/`post`/`/wait`) reuse a warm connection via `requestPooled` -> `ConnectionPool`/`KeepAliveConnection` instead of reconnecting per call; the exec WebSocket fds are per-operation and not pooled.
- **Forwarder leak + recovery.** The same close-propagation gap makes the in-VM `socat` forwarder leak connections. A `socat -T` inactivity backstop reaps them; `isx doctor` diagnoses it (host-side connection gauge in `UnixSocketTransport` / `vm status` vs the in-VM `isx-agent`'s socat count, localizing vfkit vs forwarder) and can restart the forwarder via the agent **without rebooting the VM**. `ClientLog` is a file-only (TUI-safe) diagnostic log for expected-but-noisy events like stale-connection recycling. The agent (`appliance/root/usr/local/sbin/isx-agent`, host side `VmAgentClient`) is an allowlisted one-verb-per-connection dispatcher -- `ping`, `version` (returns the appliance version from `/etc/isx-version`, cached by `VmAgentClient.applianceVersion()`; used to detect CLI↔appliance version skew in `ensureRunning`, `isx doctor`, `isx vm status`, and the TUI), `socat-count`, `sshd-status`, `forwarder-restart`, `btrfs-usage <pool> [sync]` (returns the pool's `btrfs qgroup show`/`subvolume list` output for disk accounting, since only the in-VM root agent can read the pool; the allowlisted `sync` second token forces a commit first), `btrfs-status <pool>` (the kernel's qgroup accounting flags from sysfs as `key=value` lines -- `enabled`, `inconsistent`, `mode`, `drop_subtree_threshold` -- resolved via the same mountinfo-source-device lookup as `BtrfsSysfs.java`; keep the two in step) and `btrfs-rescan <pool>` (starts a background `btrfs quota rescan`, replying `started`/`running`/`error: ...`) -- intentionally NOT a general guest-exec channel. Pool-name validation is shared by the three `btrfs-*` verbs (`valid_pool`).

**VM lifecycle locking**: `VmManager` guards mutating operations (`start`, `stop`, `restart`, `ensureRunning`) with an `fcntl` advisory file lock (`vm.lock` in `vmStateDir()`). Public methods acquire the lock then delegate to private `*Locked()` variants to avoid `OverlappingFileLockException` on same-JVM re-acquisition. When adding new operations that modify VM state, follow the same pattern: public wrapper with `acquireVmLock()` in try-with-resources, private `*Locked()` implementation. If an operation calls another mutating method (e.g. `restart` calls `stopLocked` + `startLocked`), use the locked variant directly.

**Named appliance state:** an immutable `ISX_POOL` selection namespaces every VM-owned path (disks, PID, VM lock/log/REST file, Incus and agent sockets, dummy initrd, export fingerprint, skew marker, vfkit app bundle, and instance locks) under `~/.local/state/incus-spawn/pools/<name>/`. Unset retains the historical paths exactly. Proxy files (including the persisted macOS host gateway), appliance artifacts, config, credentials, and caches are global. Named pool CPU/memory/swap values take precedence over and ignore `ISX_VM_CPUS`, `ISX_VM_MEMORY`, and `ISX_VM_SWAP`; legacy behavior is unchanged. Named pools use `VmNetwork.macForPool(name)` for a stable locally administered unicast MAC, and both vfkit launch and DHCP discovery must use `selectedMac()`. The legacy MAC remains `4a:53:58:00:00:01`. Named macOS VMs are demand-started and must never acquire a login LaunchAgent as a side effect of global proxy installation; a named proxy install removes the stale legacy whole-home VM agent, while an unset selection preserves it.

**Named vfkit exports:** `VmHostExports` resolves and canonicalizes the typed pool roots, creates only runtime/workspace, requires reference directories to exist, rejects overlap and vfkit delimiters, and translates only canonical contained host paths. vfkit attaches `isx-runtime` and `isx-reference-<name>` with the companion fork's `readonly` field and attaches `isx-workspace` without it. The appliance mirrors those modes at `/host/runtime`, `/host/references/<name>`, and `/host/workspace`; its read-only mount flag is defense in depth, not a replacement for `VZSharedDirectory` read-only enforcement. Upstream vfkit lacks this extension and must fail closed. The bounded, sorted safe reference-name list travels in `isx.reference_names`, and any named mount failure aborts appliance initialization. The resolved plan fingerprint is persisted atomically after launch, checked at the common Incus API boundary and before translating a path, and removed on stop/stale cleanup. Unset `ISX_POOL` must keep the exact `hostfs` whole-home argv and `/host` boot path.

**Exact-state container security:** Template privilege is owned by `ImageDef.security`, not branch flags. While a newly created/copied container is stopped, `BuildCommand.applyContainerSecurityPolicy()` removes inherited/pre-baked privileged mode, nesting, setxattr interception, raw LXC capability retention, raw/non-default idmap configuration, and the `tun` device before adding explicit opt-ins. Do not move these calls after start: Incus idmap changes are not live-updatable. VMs skip this Incus-side pass and receive only the in-guest policy cleanup.

**Storage pool awareness**: On a CoW-capable pool (btrfs/zfs/lvm), Incus implements a same-pool `type: copy` as a native snapshot (e.g. `btrfs subvolume snapshot`) -- no explicit snapshot API call is needed. Full copies only happen when (1) there is no CoW pool (the `dir` driver rsyncs), or (2) the source's root disk is on a different pool than the copy target (cross-pool migration). A CoW pool is **required** for instance creation and copying -- `requireCowPool()` throws with a specific diagnostic (pool listing failed vs. no CoW pool found) instead of silently falling back to the profile default. `findCowPool()` (nullable) remains for callers that handle absence gracefully (cleanup, diagnostics, TUI display, image import). `IncusClient.copy()` follows the source's pool via `planCopy()`: if the source's root disk is on a CoW pool, the copy targets the same pool; otherwise it targets the first CoW pool (cross-pool full copy). `planCopy()` also throws if no CoW pool exists. `importImage()` sends `X-Incus-Pool` targeting the CoW pool so base images don't pile up on a non-CoW default. `isx branch` and `BuildCommand.buildFromParent()` warn when a copy will be full (non-CoW), and `isx doctor` surfaces three cases -- no CoW pool (FAIL with Linux remediation), default profile root disk on a non-CoW pool (WARN with auto-fix remediation), and instances on non-CoW pools (WARN with rebuild/move guidance). `isCowDriver()` and `rootDiskPoolFromDevices()` are the unit-testable helpers.

**Default profile pool upgrade**: When Incus is set up before `isx init` (common on Ubuntu, where `incus admin init --minimal` creates a `default` dir pool), the default profile's root disk may point to the `dir` pool even after init creates a `cow` btrfs pool. `ensureDefaultProfile()` now detects this: after ensuring the profile has a root disk and NIC, `upgradeProfilePoolIfNeeded()` checks whether the existing root disk is on a non-CoW pool while a CoW pool is available, and updates it. This only upgrades (non-CoW -> CoW), never downgrades. `IncusClient.updateProfileRootDiskPool()` handles the PATCH, finding the root disk device by type rather than assuming a conventional name.

**Automation ownership, mounts, and exec:** `IncusAutomationTransport` maps the transport-neutral automation service onto Incus. An automation create must use a same-pool CoW `planCopy()` and include `user.incus-spawn.automation-key` plus source metadata in the initial copy POST; never move ownership to a follow-up PATCH. Automation mount/unmount inspects only unexpanded instance-owned devices and requires an exact object (`type`, translated source leaf, target path, and `readonly=true` only for RO); malformed, additional, or mismatched fields conflict. The mutation-side instance GET rechecks ownership/state, and its ETag is sent in `If-Match`; unmount also passes the complete map to the same conditional read-modify-write that removes it. Named macOS translation is access-aware and fingerprint-checked: workspace alone permits RW, runtime/references permit RO, and a leaf alias resolving to an export root is rejected rather than broadened. `IncusClient.execExact`/`IncusApi.execControlled` are separate from existing exec wrappers: argv remains an array, stdin is forwarded raw, and caller timeout or external cancellation makes one best-effort DELETE against the operation. Return the structured termination and DELETE acceptance rather than claiming the guest process tree was killed. That stronger behavior requires live Incus verification on Linux and through macOS vsock.
